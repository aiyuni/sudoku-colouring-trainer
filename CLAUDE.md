# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Client-only React 19 + TS + Vite app (deployed to GitHub Pages) for solving/teaching Sudoku with human techniques, centred on Colouring: Simple Colouring, 3D Medusa, and **Dragon Colouring** (a novel Medusa extension invented here). All code is in `frontend/`.

If my request is ambiguous, ask one clarifying question before doing anything.

## Commands (run in `frontend/`)

- `npm run dev` (port 5173) · `npm run build` (`tsc -b && vite build`) · `npm run lint` (oxlint)
- **No test framework.** The type-check in `build` is the only gate, except for OCR: `npm run test:ocr` runs every screenshot in `frontend/ocr-fixtures/` (`manifest.json`: image + the puzzle string it shows) through the real `ocrGrid` + Tesseract in Node (`NodeGridImage.ts`) and diffs every cell. Run it before and after any OCR change - a fix for one screenshot style must not break another - and add every new example screenshot the user provides as a fixture (`imageOverrides` for cells where the screenshot and its string disagree). `scratch-*.ts` are ad-hoc harnesses outside `tsconfig` (`include: ["src"]`) with no configured runner.
- tsconfig is strict about: `erasableSyntaxOnly` (no enums/param properties), `verbatimModuleSyntax` (`import type`), `noUnusedLocals/Parameters` (unused code fails the build).
- CI deploys on push to `master`; `VITE_BASE` sets the asset base path.

## Architecture

**`src/sudoku/`** - pure logic, no React. Data shapes (`types.ts`): `Board` (0 = empty), `CandidateGrid[row][col][digit-1]` (pencil marks are *app state, not derived*: finders trust them as given), `CandidateColorGrid` (manual user paint, unrelated to technique colouring). After placing a digit call `SudokuRules.eliminatePeerCandidates` or stale marks cause wrong hidden singles.

Each technique is a `Sudoku*Finder` class whose `find*` methods return instances (basis cells + eliminations/solves) and never mutate. Difficulty order (the user's, and what the `RANK_*` tiers encode): Single → LockedCandidate → Pair/NakedSubset/HiddenPair → UniqueRectangle (all types) → BUG+N (BUG+1/2/3) → Avoidable Rectangle → BivalueOddagon → Color (Simple Colouring 1-2) → X-Wing → Short Single-Digit AIC → Finned X-Wing → Short AIC → Swordfish → Finned Swordfish → Medusa (`findChains`, `findMassElimination` = rules 1-2, `findRule3/4/5Eliminations`) → Generic AIC → ALS-xz → Dragon → Double Dragon → Dynamic Dragon → Double Dynamic Dragon.

- **Unique Rectangle** (`SudokuUniqueRectangleFinder`): one finder covers Types 1, 2, 3, 4, 5, 7a, 7b, 7c, and 7d (Hidden Rectangle) - all exploit the same "4 cells spanning exactly 2 rows/2 cols/2 boxes, all restricted to the same 2 candidates" deadly-pattern (if all 4 held only that pair, the puzzle would have a second solution via diagonal swap, which a uniquely-solvable puzzle can't). `find()` enumerates every such rectangle, tries every applicable sub-type per common digit pair, and returns a flat `UniqueRectangleInstance[]` (`type: string` - normally one literal name, see below) sorted simplest-type-first (`priorityOf`). Each instance carries `reasons` (one per reasoning path: type, bare "where" clause, that path's own eliminations/solves), a conclusion-free `reasonText` built from them (Dynamic Dragon's clause builders in SudokuDragonFinder.ts append their own "which eliminates ..."), and `reasonCells` (the specific cells that justify the elimination, distinct from the full 4-cell rectangle). The Techniques panel uses `explainUniqueRectangle(ur, candidates)` instead: each clause followed by its own conclusion, a cell the eliminations cut to one candidate stated as a placement ("r1c4 is 6") and peer eliminations of that digit left unsaid, clauses from the same source (and all Type 7d paths) folded together. **Wording only** - it never changes `eliminatedCandidates`/`solvedCandidates`, which are what Apply, Dragon and the generator use. Type 7d's `type` is plain `'Type 7d'`; "Hidden Rectangle" is a panel display name added in techniqueEngine.ts. `hasStrongLink(board, candidates, a, b, digit)` (a general conjugate-pair check across every unit the two cells share) underlies Types 4/7a/7b/7c/7d. Only Type 1 ever produces a `solvedCandidates` entry (a single extra-candidate cell forced to the non-pair digit); every other type is elimination-only.
  - **Suppression and merging**, both per rectangle+digit-pair, in this order, before the sort: `suppressType7bAnd7dCoveredByType4` drops any Type 7b/7d instance whose own eliminations are already fully covered by a Type 4 instance found for the same pair - verified by a 1500-puzzle sweep that whenever Type 4 applies, 7b and 7d *always* independently rediscover it too (Type 4's "digit locked to the 2 non-bivalue cells via a strong link" is exactly the strong link 7b's chain and 7d's opposite-corner check are each built to notice), so without this a Type-4 rectangle would always also show two redundant rows re-explaining the identical conclusion. It only suppresses what's fully redundant, though - the rare case where 7b/7d's own chain also proves something *beyond* Type 4's own conclusion is left alone. `mergeSameRectangle` then folds every remaining instance that shares the same 4 cells + digit pair into one row regardless of type (a bivalue cell's digit can carry a strong link via its row *and* a separate one via its column at once, so more than one type, or more than one reasoning path within one type, can each independently justify a *simultaneous* elimination on the same rectangle) - listing these separately was actively misleading, not just noisy: applying one commonly breaks the strong link another row's own proof depended on, so that row would silently vanish from the next recompute, indistinguishable from "Apply also affected the other row". A merged instance's `type` becomes "Type X" unchanged (one type, several reasoning paths) or "Types X & Y" (more than one type contributed); `priorityOf` recovers a real `TYPE_PRIORITY` key from either shape for sorting.
  - Types 2/3/5 follow HoDoKu's definitions. **Types 2/5** (`findType2Or5`): every extra-candidate corner holds the pair plus the same single extra Z. That's Type 2 when there are two corners sharing a row or column, and Type 5 when they're diagonal or there are three. Z is eliminated from every cell seeing all of them. **Type 3** (`findType3`): two side-by-side extra corners act as one virtual cell holding their extras (at least two digits). The finder looks for a naked subset of any size in each shared house (the user's reference example needs a 5-digit one) and eliminates from every house the whole subset lies in. Only the smallest eliminating subset per house is reported. Its non-UR partner cells go in the instance's optional `subsetCells`, which the panel's `usedCells` and Dynamic Dragon's `basisCells` include. `find(..., { mergeTypes: false })` skips `mergeSameRectangle`; only the tutorial uses it, so a lesson teaches one type's own eliminations.
  - Adding a further UR sub-type means: extend `UniqueRectangleTypeName`, add a `findType*` method that pushes onto its `out` array with its own `reasonText`, and give it a `TYPE_PRIORITY` entry - no other file needs to know about the sub-type split, since callers only ever see the unified `UniqueRectangleInstance[]`.
- **Fish** (`SudokuFishFinder`): X-Wing, Finned X-Wing, Swordfish, Finned Swordfish (`FishTechnique`), each OFF by default behind its own Settings → Techniques toggle (`xWingEnabled` etc.; the engine takes them as one `enabledFish` set, last param of `buildTechniqueInstances`/`buildSolvePath`). Internally the general base/cover set rule (`evaluateFish`: fins = base candidates in no cover set; eliminate cover candidates that aren't base candidates and see every fin) - but the UI never says "base"/"cover", only "5 in rows 2 and 5 is confined to columns 5 and 8, apart from the fin at ...". Sashimi fish are deliberately excluded (each base line must keep 2+ candidates inside the covers). Verified against HoDoKu's example grids and a random-state soundness sweep. Each fish is its own `RANK_*` tier. In `buildTechniqueInstances` the fish and short-AIC rows are gathered, sorted by rank and pushed via `pushUnlessCoveredByEasier` (a row whose eliminations strictly-lower-ranked rows already make in full is hidden); Generic AIC goes through the same helper after Medusa. Usable inside Dynamic Dragon (the four `FishTechnique` strings are `Rule3Technique`s; `findExtensionRule3Move` tries them interleaved with the AIC kinds per `FISH_AND_AIC_RULE3_ORDER`, after BUG+N/Oddagon - so with both short AIC kinds allowed, single-digit AICs now always get first refusal over general Short AICs), excluded from `DEFAULT_RULE3_TECHNIQUES`, and `effectiveAllowedRule3Techniques` drops any fish not enabled in Settings (master switch, like the AICs). No auto-solve button, by request. The Dragon puzzle generator gets `enabledFish` too: an enabled fish rejects a 'medusa'/'dragon' checkpoint (not 'simple-colouring': fish rank above it) and joins the solving grind after Simple Colouring (no separate "disregard" setting).
- **Named Short Single-Digit AIC patterns** (`SudokuShortAicFinder.ts`): Skyscraper, Two-String Kite, Crane, Empty Rectangle are *patterns, not techniques* - same toggle, auto-solve button, rank, `'short single-digit aic'` Rule 3 tier. `ShortAicInstance.pattern`/`patternText` carry the name, which every display of a single-digit AIC shows instead of "Short Single-Digit AIC" (panel row name, hint label/blurb/steps, Dynamic Dragon clauses and row name). Skyscraper/Kite/Crane are names given to plain chains `A = B - C = D` by `classifySingleDigitPattern`, which ports Sudoku.Coach's own solver conditions (from its JS bundle - the learn pages are client-rendered). Empty Rectangle is a *grouped* chain the link graph can't find: `findEmptyRectangleIntersections` (every ERI, stored as its own query) + `findEmptyRectangles` (ERI + a row/column conjugate pair crossing one arm; boxes of 3+ candidates only - with 2 it is a Crane/Kite already). A grouped node has `AicCandidate.cells`; use `aicNodeCells`/`aicNodeText`/`aicChainView`, never `row`/`col` alone, and the grid overlay outlines groups (`fromCells`/`toCells` on `AicLinkRef`). `findRectangleEliminations` (sudokuwiki's replacement method) is not used by the app: it is the independent cross-check for Empty Rectangle. `pickBestPerEliminationSet` prefers named patterns among tied single-digit chains. `dragon-research/er/sweep.ts` checks soundness, ER = Rectangle Elimination, and the names against a port of Sudoku.Coach's three algorithms (19k states, 0 mismatches, 2026-09-30).
- **BUG+N** (`SudokuBugPlusNFinder`): BUG+1, BUG+2 and BUG+3 are **one technique** internally (one `RANK_BUG_PLUS_N`, one `'BUG+N'` Rule3Technique/Dynamic Dragon checkbox, one auto-solve button), but the UI always names the specific one ("BUG+2" - `bugPlusNName`; ids are `bug-plus-n-<N>-...`, which hints and `tutorialTargetFor` read; Dynamic Dragon substeps carry `displayName` for `dynamicDragonLabel`). Every unsolved cell bivalue except N = 1-3 cells with exactly three candidates. Each tri-value cell's extra ("BUG") digit is found by trying every one-digit-per-cell choice (<= 27) and keeping one whose removal leaves a true BUG (every unplaced digit exactly twice in every unit) - at least one BUG candidate is then true. BUG+1: that candidate is the cell's solution. BUG+2/3: eliminate every candidate false alongside each BUG candidate - in practice the shared BUG digit from cells seeing all N (the user's example: 2 in r2c2 {1,2,8} and r8c9 {1,2,6} => r8c2 is not 2). **Only the BUG digit, not any digit the cells share** - the "shared candidate" shortcut is unsound (69 wrong eliminations in the sweep). Sweep 2026-09-30: 4669 puzzles / 341k solve-path states, 137 BUG+1, 67 BUG+2, 32 BUG+3, 0 wrong. The old BUG+1 finder only counted "3 times in a unit" without checking the rest pairs up, and was wrong whenever a hidden single was still on the grid; BUG+1 now goes through the same full check (same answer wherever the old one was right). `find()` returns at most one instance. `dragon-research/bug-n/` holds the soundness sweep (`sweep.ts`), the random-true-state lesson miner (`mine.ts`) and a lesson check. Saved settings with the old `'BUG+1'` Rule3 name are migrated in `persistedState.ts`.
- **Avoidable Rectangle** (`SudokuAvoidableRectangleFinder`): a Unique Rectangle whose corners are partly *solved* - by the solver, never givens (a given corner is what stops the swap, so no contradiction). Type 1 (SudokuWiki's form): three solved corners, A on two diagonal ones and B on the third, so the fourth can't be B. Type 2 (HoDoKu's): two side-by-side solved corners A and B, and the other two hold only their pattern-completing digit plus the same extra X, so X goes from every cell seeing both. 4-cell patterns only, by request (no extended/6+ cell forms). **The one technique that needs the givens mask**: `buildTechniqueInstances`/`buildSolvePath`/the solve-path worker request, the Dynamic Dragon helpers and `SudokuDragonTargetFinder` all take `givens` (last param / `DragonExtendOptions.givens` / `DynamicDragonLimits.givens`); without it (null) the finder returns nothing. Always on, `RANK_AVOIDABLE_RECTANGLE` right after BUG+N, own auto-solve button. `'avoidable rectangle'` is a `Rule3Technique` (Dynamic Dragon treats the assumed side's cells as solved non-givens; the finder memo key includes the givens) but is excluded from `DEFAULT_RULE3_TECHNIQUES`, by request. Generated puzzles load with every filled cell a given, so it can't apply at a generator checkpoint - it's only in the generator's solving grind. The tutorial lesson needs `decodePuzzleState(board, removed, clues)` so solved cells aren't drawn as givens. `dragon-research/avoidable-rectangle/sweep.ts` checks soundness/frequency and mines lesson positions.
- **Bivalue Oddagon** (`SudokuBivalueOddagonFinder`): an odd-length (5, 7, 9, ... up to `BIVALUE_ODDAGON_MAX_LENGTH`) loop of cells all holding the same two candidates, each linked to the next by sharing a unit - an odd loop that's *entirely* that pair is a deadly pattern, so 1-3 loop cells ("guardians") holding one shared extra candidate are what keep it from actually occurring. Type 1 (one guardian): that candidate is the guardian's solution. Type 2 (two or three guardians): eliminate it from any other cell that sees every guardian. Cycle-finding is a DFS per digit pair (36 pairs); `MAX_NODES_PER_PAIR`/`MAX_SEARCH_STEPS` cap the cost against a pathological candidate grid (real ones have only a handful of eligible cells per pair) - any change here should be re-checked against those caps with an adversarial all-one-pair grid, not just realistic puzzles.
- **ALS-xz** (`SudokuAlsXzFinder`): singly linked only, per HoDoKu's ALS page (doubly linked, ALS-XY-Wing, ALS chains and Death Blossom deliberately not implemented). ALS = N unsolved cells of one house with N+1 candidates (a bivalue cell counts); RCC X = every X in A sees every X in B (overlap may not hold X, which falls out of "a cell never sees itself"); Z = any other common digit, eliminated from cells seeing every Z in both. A pair with two RCCs is reported once per RCC, singly linked. Two ALS that fit in one house together are skipped (`houseMask`): that is always a naked set (of their union, or of the overlap alone), never a real ALS-xz - see the class comment for the counting argument. 81-cell sets are three 27-bit words. `find()` sorts fewest-cells-first and drops a pair whose eliminations one simpler pair already makes. Off by default (`alsXzEnabled`, Settings → Techniques), ranked `RANK_ALS_XZ` after Generic AIC; `'als-xz'` is a `Rule3Technique` tried last in `FISH_AND_AIC_RULE3_ORDER`, excluded from `DEFAULT_RULE3_TECHNIQUES`, master-switched like a fish, and only its first (simplest) result is memoized. **Never auto-solved**: no button, and the Dynamic Dragon auto-solve skips any chain that used it. The generator treats an enabled ALS-xz like a fish, but it only rejects a 'dragon' checkpoint (it ranks above Medusa). Verified against HoDoKu's two ALS-XZ examples (`axz01`, `axz02`) and a random-state soundness sweep.
- Both BUG+N and Bivalue Oddagon are usable *inside* Dynamic Dragon (`'BUG+N'` / `'bivalue oddagon'` in `Rule3Technique`), on by default (`DEFAULT_RULE3_TECHNIQUES` excludes only the AIC kinds) - toggled the same generic way as every other Dynamic Dragon technique, via the `ALL_RULE3_TECHNIQUES`-driven checkbox list in App.tsx's Settings. In `findExtensionRule3Move` a BUG+1 is always a direct solve (returns immediately, never a chain antecedent); a BUG+2/BUG+3 only eliminates, so it chains like Oddagon Type 2.

`SudokuDragonFinder.extend(medusaChain, board, candidates, {dynamic, allowedRule3Techniques, aicLimitPerStep})` is the core. Only valid on a *stuck* Medusa chain (none of rules 1-5 apply; callers check). Returns an ordered `DragonMove[]` log; the UI replays it and derives state by folding moves (`foldDragonMoves`). `optimize: true` ("Optimize Dragons" setting, default OFF) searches, per elimination phase, over every candidate either colour could extend with, for the path reaching an elimination with the fewest extensions - never worse than, and resolving exactly the same chains as, OFF (see the handoff). `optimizeDynamic: true` ("Optimize Dynamic Dragons", default OFF) also branches on every Extension Rule 3 move, for Dynamic Dragons. `dynamic: true` adds Extension Rule 3 (`findExtensionRule3Move`: simulates naked pairs/locked/UR/hidden pairs/AICs on a cloned board under a side's assumption; "naked pair" is always allowed). Outside that simulation it works from the original candidates and does not re-derive conjugate pairs as eliminations accrue.

**Double Dragon Colouring** (`doubleDragonEnabled`, OFF by default, Dragon Configuration menu; `RANK_DOUBLE_DRAGON` between Dragon and Dynamic; no auto-solve button, by request; the user's own experimental technique): for an ordered pair of chains plain Dragon is stuck on, `stuckColouring` keeps the first Dragon's dead-end colouring (extend() discards it), and `extendDouble` runs a plain Dragon on the second chain with one extra extension, the *Dragon link* (`takeDragonLink`, tried per side after Rules 1-2/hidden single): a second-Dragon node of side X that can't be true together with a first-Dragon node of side S (weak link) proves X => S', so all of S' is coloured as X's dragon colour (`findDragonLinkMove`, a pure function of the colouring). Link *conclusions* are checked with the elimination rules (`findDragonLinkConclusion`): X linked to both first sides, or linked while an S' node is an X' Medusa colour => X false; X and X' both linked to the same S => S' true (a move about the first Dragon's colours, `secondDragon: false`). Exhaustive and Optimize Dragons work exactly as for a plain Dragon (the link is one more branch in `extendOptimized`'s search; Optimize never changes whether a pair resolves); never Dynamic. The panel's "3+ base Medusa candidates" filter applies to the *first* Medusa. The log is the first Dragon's stuck moves then the second's (`DragonMove.secondDragon`: its `blue/darkBlue/yellow/orange` are displayed pink/purple/lime green/dark green, the palette's swatches 3/7/6/8, via `foldDragonMoves`' extra lists and `technique-pink/-purple/-limegreen/-darkgreen`). `foldDragonMoves` keeps each Dragon's colour separately, so a candidate both Dragons colour (an absorbed yellow/orange one, or a first-Dragon node in the second Medusa) is drawn as a split pip (`renderDragonSplit`, first Dragon bottom-left). `findDoubleDragons` (shared by the engine and the generator) skips pairs with no weak link between the two stuck colourings - exact, since the second Dragon is identical to its stuck plain run until its first link. Verified sound (0 wrong eliminations/placements, 0 true-side nodes false) over every plain-stuck state of the Dynamic stock and ~280 generated puzzles, see DRAGON_COLOURING_HANDOFF.md. The "Generate Double Dragon colouring puzzle" button (enabled only while the technique is ON) serves `DOUBLE_DRAGON_PUZZLE_STOCK` via `pickStockDoubleDragonPuzzle` (generator option `requireDoubleDragon`: plain Dragon fails on every chain, a Double Dragon progresses) - such positions are far too rare to find live. "Dynamic Dragon puzzles must not allow double Dragons" (`dynamicDragonPuzzleForbidsDoubleDragon`, only settable while "must not allow plain Dragon" is ON) adds generator option `forbidDoubleDragon`: the Dynamic stock picker then skips entries a Double Dragon progresses (`pickFromStock` tries the next entry when one no longer verifies). Both stocks hold only positions with no AIC, fish or ALS-xz at the start (26 Double, 42 Dynamic-only as of 2026-09-29; target 42 each - the Double search was stopped at 26, restart `dragon-stock-pending/genboth.ts` to continue) - see DRAGON_COLOURING_HANDOFF.md's Double Dragon section.

**Double Dynamic Dragon Colouring** (`doubleDynamicDragonEnabled`, OFF by default, Dragon Configuration → Dynamic Dragon Colouring; off while Dynamic Dragons are disabled; `RANK_DOUBLE_DYNAMIC_DRAGON`, the top tier; no auto-solve): Double Dragon Colouring where the Dragons may use Extension Rule 3 - `findDoubleDragons(..., { dynamic: limits })`, so both chains are ones single Dynamic Dragon is stuck on. `computeDoubleDynamicDragonExtensions` keeps a result only if some step of either Dragon is an `extension-rule3` move (otherwise it would be a plain Double Dragon), and skips pairs plain Double Dragon resolves while that is enabled. Follows the Dynamic settings (techniques, AIC limit, max techniques per step - per Dragon), Exhaustive and Optimize Dynamic Dragons (implies the optimized search); the 3+ base filter applies to the first Dragon. Also in the solve path and Find by elims (which now searches plain Double Dragon too, when enabled). Same colours as Double Dragon (`extendDouble` also renames a second-Dragon step's substep clauses). "Generate Double Dynamic Dragon Colouring puzzle" (needs the setting) serves `DOUBLE_DYNAMIC_DRAGON_PUZZLE_STOCK` - whole Sudoku.Coach states (mid-solve positions), served as-is - where nothing else progresses even with every technique and no limits.

Performance-critical: this is the most-optimized code path in the app - it runs live on every board/candidate change, from the solve-path search (potentially hundreds of times per search), and hundreds of times per generated puzzle.
  - `extend`'s main loop memoizes a "found nothing" answer per side, covering Extension Rules 1, 2, 3 *and* the hidden-single check together (`findExtensionForSide`), keyed on that side's node count (and `candidatesVersion` in exhaustive mode) - all four are pure functions of that side's own coloured cells, so once a side's turn comes up with nothing, it stays that way until the side gains a cell or (exhaustive) an elimination lands. Without this, both sides' full battery re-runs on every alternating turn.
  - `findExtensionRule1Move` indexes the current primary colour's nodes by digit up front instead of rescanning the whole node map per cell.
  - `sudokuUnits()` (`SudokuUnits.ts`) is cached after its first call - the 27 row/column/box arrays never change, and this is called inside every one of the hot loops above.
  - Extension Rule 3's AIC search (`aicsInOrder`) builds one `LinkGraphs` (`buildLinkGraphs`) and passes it into both `findShortAics` and `findGenericAics` (both take an optional `graphs` param) instead of each rebuilding an identical graph for the same hypothetical board - only matters when both actually run in the same step, which "Limit to 1 AIC per step" OFF makes common.
  - `findNakedTriplesAndQuads` (`SudokuNakedSubsetFinder.ts`) computes triples and quads together, sharing the per-unit eligible-cells scan, for the same reason `findNakedTriples`/`findNakedQuads` back to back in Extension Rule 3 were doing it twice.
  - `findEliminationMoves` first asks the exact, table-based `hasAnyElimination` (almost every call - one per colouring the Optimize search tries - finds nothing); Rule 1/Rule 2 scans use the same "which cells see (side, digit)" table (`seenByNodes`) instead of rescanning every node per cell. Both must stay exactly in step with the rules they shortcut.
  - Extension Rule 3's technique finders are memoized by the whole hypothetical grid (`memoFind`/`gridKey`, bounded LRU `FINDER_MEMO_MAX_ENTRIES`, kept across calls): the default path, Optimize's fallback and Optimize Dynamic's every-move simulations step through identical grids, and ~45% of finder calls on a long solve path were repeats. Finder results are shared, so they must never be mutated downstream.
  - Any change here should be checked against a saved "before" copy of `src/` across many realistic puzzles/settings combinations (step-by-step signature match, not just wall-clock) - see the equivalence-sweep pattern used to verify all of the above with zero behavioural difference.

Other: `SudokuSolver` (backtracking, counts ≤2 solutions; validation only, not the human path), `SudokuDragonPuzzleGenerator` (grinds for puzzles where only Dragon/Dynamic Dragon can progress from a fresh autofill - or, with `target: 'simple-colouring' | 'medusa'`, where that technique is the easiest move, AIC checks skipped; App runs it through `generateDragonPuzzleInParallel` in `ParallelDragonPuzzleGenerator.ts`, one Web Worker per spare core racing independent random grids, first hit wins, main-thread `generate` as fallback; with the "must not allow plain Dragon" setting ON, Dynamic Dragon puzzles instead come from a pre-generated stock, `dynamicDragonPuzzleStock.ts`), `PuzzleImporter` (81-char string, Sudoku.Coach `SCv7_32_` state, SudokuWiki text; "Copy Puzzle As-Is" exports the SC state plus an extra `sudokuSolverPaint` JSON key holding the candidate paint by `CANDIDATE_COLOR_ORDER` position, which SC ignores - that order must never be reshuffled; "Copy Original" is the plain givens string), OCR (`SudokuGridOcr` over a `GridImage` abstraction, `CanvasGridImage`, tesseract.js in `OcrDigitRecognizer`; a screenshot import loads its digits editable with a proofread banner above the import box - `ocrProofread` in App.tsx, screenshot preview + "Lock as givens", which turns every filled cell into a given as one undoable step; while it is pending the grid is saved already locked, so a reload counts as locking).

**`src/techniqueEngine.ts`**: pure (no React/DOM) home of `TechniqueInstance`, the `RANK_*` tiers, the shared finder instances, `buildTechniqueInstances`, the Dragon compute helpers and `buildSolvePath` - split out of App.tsx so `solvePath.worker.ts` can import it. `solvePathInWorker(board, candidates, SolvePathOptions, signal)` runs one search per fresh worker (abort = terminate), falling back to the main thread without Workers.

**`src/App.tsx`** (all UI + orchestration; styles in `App.css`):
- `buildTechniqueInstances()` recomputes a flat `TechniqueInstance[]` (simplest-first) on every board/candidate change; it drives the Techniques panel and click-to-highlight (yellow = basis, red = eliminated, green = solved, blue/yellow chain colours, AIC links, Dragon stepper).
- **Adding a technique = new finder in `sudoku/` + a block in `buildTechniqueInstances` (`techniqueEngine.ts`; incl. a `techniqueRank`, in its place in the difficulty order) + (normally) an Auto-solve panel button.** Two more hardcoded finder lists must also learn about it, or Dragon-only puzzles can turn out solvable by it: `SudokuDragonPuzzleGenerator` has both a "nothing easier than Dragon applies" check and a separate solving grind. If it should be usable *inside* Dynamic Dragon, also extend `Rule3Technique` / `ALL_RULE3_TECHNIQUES` / `findExtensionRule3Move` in `SudokuDragonFinder.ts` and `RULE3_TECHNIQUE_LABELS` in App.tsx.
- `buildSolvePath`: at each step, picks among every currently-applicable `TechniqueInstance` with `pickGreedyInstance` (default) or `pickEasiestInstance` (`easySolveEnabled` setting, "Easy Solve" checkbox on the Solve Path tab); `solvePathTimeoutMs` setting (default 12s, "Timeout" select on the Solve Path tab) / 200-step budget; runs in a Web Worker (Generate is cancellable from the busy indicator); one Dragon chain = one step. Heuristic, not minimal. The "Solvable / Solvable with brute force" verdict under the grid is this same search (whichever picker is active, same timeout) from a fresh autofill, also in a worker (`solvabilityRequest` effect; a newer board/settings change terminates the old search; shows `checking` meanwhile): only a search that gets *stuck* means brute force; one that runs out of time or steps is reported as `solvable-unknown` (it used to be misread as "brute force", so ticking more Dynamic Dragon techniques - slower per step - made solvable puzzles look unsolvable). Cached in state and stored in each undo history entry. Applying a step drops it from the cache without recomputing; the path is flagged stale when the board drifts from the next step's `boardBefore`. With every Dynamic Dragon technique ticked (all three AIC kinds included) and Exhaustive off - the slowest realistic combination - see the `extend`/`sudokuUnits`/AIC-graph/naked-subset optimization notes above.
  - `pickGreedyInstance`: most cells solved, then most candidates eliminated, then (on a full tie) lowest `techniqueRank` - the simplest technique wins a tie instead of whichever happened to be found/listed first.
  - `pickEasiestInstance` ("Easy Solve"): lowest `techniqueRank` first, full stop - ignores progress entirely, so a Naked Single always beats a Dragon chain that would solve half the grid. Ties go to fewest Dragon Colouring steps (`instance.moves.length`, 0 for non-Dragon techniques so that tier is a no-op between two of those), then most candidates eliminated.
  - `TechniqueInstance.techniqueRank`: a difficulty tier set at every construction site in `buildTechniqueInstances` (the `RANK_*` constants just above it), in the same order the difficulty order above lists. A new technique needs a rank there too.
- `computeStuckDragonExtensions` / `computeStuckDynamicDragonExtensions` are shared by the panel and auto-solve buttons; a chain plain Dragon resolves is never also listed as Dynamic. Short-AIC toggles are master switches over the Dynamic Dragon checkboxes (`effectiveAllowedRule3Techniques`).
- Grid changes go through `commitGrid(next, nextSolvePath?)` (undo/redo; omit the second arg to carry the cached path forward, pass `null` to clear). Auto-solve buttons use `commitAutoSolve`, which clears the path.
- **Keyboard shortcuts** (`src/hotkeys.ts`, Settings → Keyboard shortcuts via `HotkeySettings.tsx`; the `hotkeys` AppSetting): only fire inside elements marked `data-hotkey-scope` (the grid and the Solution/Candidates/Candidate Colours/Highlight pads), checked in App's `onKeyDown` before plain digit/arrow entry. The paste shortcut, while it is Ctrl+V, is served from the native `paste` event (`onScopedPaste`, no permission prompt); any other binding uses `navigator.clipboard.read()`. Text is tried as a puzzle string first, then an image goes to OCR.
- **Busy indicator** (`BusyIndicator.tsx`, `busyTask.ts`): a new long operation goes through `runBusyTask(kind, {title, detail, onCancel?}, work)`, which shows the indicator + progress cursor, starts `work` only after a paint (`afterPaint`), and clears it in a `finally`. The Techniques list is computed from `analysis` (`useSettledValue(liveAnalysisInputs)`, one painted frame behind the live board/settings) so the indicator is on screen before it blocks - a new input to it must go into `liveAnalysisInputs`. Async work that commits a grid when it finishes must use `latestRef.current.commitGrid`, not the closure from when it started (the page stays usable meanwhile, so that closure's grid/history may be stale).
- Persisted state (`localStorage`): custom swatch colours/shapes (App.tsx), and via `src/persistedState.ts` the current grid (board, givens, candidates, candidate paint - saved on every `grid` change) and every `AppSettings` value (the `currentSettings` snapshot in App), both validated on load with a fallback to defaults. Undo history, the Solve Path and view state are deliberately not saved. Plus usage analytics' own visitor/visit ids.
- **Import analytics**: `reportImport` (`src/importAnalytics.ts`) fire-and-forgets each successful string/OCR import to the Cloudflare Worker in `analytics/` (repo root, own `package.json`/wrangler, stores in D1; see `analytics/README.md`). Only active when `VITE_ANALYTICS_URL` is set at build time (CI reads the `VITE_ANALYTICS_URL` repo variable). The Worker bundles `SudokuSolver` straight from `frontend/src/sudoku/` to set `is_valid_puzzle`, so keep that file free of browser-only dependencies. A new import path must call `reportImport` too. Device/OS/browser columns come from the Worker's own User-Agent parser (`analytics/src/device.ts`, hand-written - ua-parser-js v2 is AGPL), helped by hints the page sends (touch points for iPads posing as Macs, Chromium Client Hints for the real model/OS version). A new D1 migration must be applied (`npm run migrate:remote`) before the Worker that writes it is deployed.
- **Usage analytics** (`src/usageTracking.ts`, started in `main.tsx`): a visitor id in `localStorage`, visits split after 30 min idle, *engaged* time per "area", and merged events. They are batched to the Worker's `POST /sync` and stored in `visitors`/`visits`/`visit_areas`/`events` (never `puzzle_imports`). They're read on the Worker's `/admin` dashboard behind the `ADMIN_PASSWORD` secret (`analytics/src/admin.ts`, `dashboard.admin.js`).
  - Areas come from `useAnalyticsArea(name, AREA_LAYER.x, active)`: in App, the Techniques-panel tab with the selected technique, and the compact dock tab; each `DropdownMenu` (`trackingName` prop); HelpModal; TutorialPage and its sub-tabs. A new menu, modal or overlay should register one.
  - Buttons are counted by one delegated click listener (visible label, digits -> `#`, grid cells skipped). Settings are tracked through the `currentSettings` snapshot in App (also what gets saved), so a new setting goes there too. `runBusyTask` records every long task's outcome and duration.
  - All of it is fire-and-forget and must never throw into the app.
- **Generic AIC** (`SudokuGenericAicFinder`): AIC chains longer than Short AIC's 5 links, up to `GENERIC_AIC_MAX_LENGTH` (top of that file - the one number to change; it is a breadth-first search, so length barely affects speed). Same shape (`ShortAicInstance`), same settings pattern as Short AIC: `genericAicEnabled` (needs Short AIC on, confirm dialog), `'generic aic'` in `Rule3Technique`, its own auto-solve button, and `dragonGenerationDisregardsGenericAic` for the generator. Panel rows are suppressed when an easier technique (incl. Short AIC) already makes the same eliminations.
- **Dynamic Dragon substep player**: an Extension Rule 3 move's `description` only names its techniques (`'Assuming light blue is true, then we have a naked pair, which reveals a short single-digit AIC (Type 1). As a result, ...'`); the detail is in `DragonMove.substeps` - one entry per technique in the chain, each with its own "which eliminates ..." clause, basis cells, and hypothetical eliminations (drawn as a hollow red circle+cross, `technique-hypothetical-elimination` in App.css - generalized from AIC-only to every technique), then a final `'dragon colour extension'` substep for the colouring itself. `DragonStepper`'s second, separate forward/rewind row (`dragonSubstepIndex` state, rendered when `substeps.length > 1`, i.e. always for these moves) reveals them one at a time; the default, unnavigated view still shows every substep at once. See DRAGON_COLOURING_HANDOFF.md's "UI replay" section for the memo chain (`dragonTechniqueCellKeys`/`dragonAicChains`/`dragonAssumedEliminations`) this drives.
- **Find by elims** (third Techniques-panel tab): `SudokuDragonTargetFinder` takes candidates the user wants eliminated (`8r2c3, 2r3c4`), validates them (readable, still marked, not the puzzle's true digit), then searches every stuck chain's plain and Dynamic Dragon log (always Exhaustive and always Optimize Dragons, regardless of either setting) for the earliest move whose accumulated effect covers them all. Winner = fewest *other* eliminated candidates, then fewest steps. Its result is a normal `TechniqueInstance` (via `buildDragonInstance`), so the grid highlights it and Apply commits it like any Dragon row; it goes stale when the grid changes.
- **Autocomplete Colours** (fourth Techniques-panel tab): the user paints a Medusa start in two colours (the first two painted, in swatch order); `autocompleteMedusa` (`SudokuMedusaAutocompleter.ts`) validates it against `buildStrongLinkGraph` (every seed linked, one component, parity matches) and returns the full chain, which App paints (one undoable step, user paint kept) and runs through `buildMedusaChainInstance` - the same per-chain builder the Techniques list's Medusa rows use, so changing one changes both. Result goes stale like Find by elims; Apply commits it. While shown, the chain's own candidates skip the solved/eliminated/used highlights (`autocompleteChainKeys`) so they keep the user's paint colours. Its **Autocomplete Dragon (Plain)** button takes 3-4 painted colours (first two = Medusa, the rest dragon colours; a lone dragon colour's side, or a swapped pair, is inferred by trying both), checks and continues the colouring with `autocompleteDragon` -> `SudokuDragonFinder.continueColouring` (plain: Exhaustive/Optimize from settings; **Autocomplete Dynamic Dragon**: the exact options `computeStuckDynamicDragonExtensions` passes, and painted candidates may also come from Extension Rule 3, checked with the every-move `extensionRule3Moves` enumeration), and shows the log in the normal `DragonStepper`, opened at the user's last own step, with the grid and text in the user's swatches.
- **Hint popup** (Techniques tab's Hint button, `HintModal.tsx`): hints about `pickEasiestInstance(techniqueInstances)`, revealed one at a time: name, then per-technique advice (`hints.ts`, derived from the instance's own fields), then the answer. A 3D Medusa or single plain/Dynamic Dragon instead reads the user's paint like Find by colours (`checkMedusaPaint`, then App's `checkPaintedDragon` - the checking half of Autocomplete Dragon) and names the next candidate to colour and why. Reopening it for the same technique keeps what was revealed up to the first changed hint. A new technique needs a `techniqueHintLabel`/`techniqueBlurb`/`detailSteps` case (it falls back to name + answer). The first hint carries a "Learn this technique" link to the How It Works tab/sub-tab teaching it, from `tutorialTargetFor` (`src/tutorial/tutorialLinks.ts`, keyed by instance id, sub-tabs by `LessonGroup.title`); a technique the page doesn't teach returns null and gets no link.
- **How It Works page** (`src/tutorial/`, opened from the toolbar and the help modal): nothing is hand-drawn. `tutorialExamples.ts` lists real positions (81-char board + removed marks), `lessonBuilders.ts` turns them into captioned frames using the app's own finders and Dragon move logs, `TutorialGrid` reuses the main board's CSS classes. Basics and Abusing Uniqueness (UR Types 1/4/7a-7d, BUG+1, BUG+2, BUG+3 - separate sub-tabs, Bivalue Oddagon) are split into sub-tabs, one `LessonGroup` per technique (`buildBasicsGroups`/`buildUniquenessGroups`); the uniqueness positions were mined from real solves as the first stuck point after the Basics, and need no removed marks. **Adding a lesson for a technique (or renaming a sub-tab) means updating `tutorialTargetFor` in `tutorialLinks.ts`**, so the Hint popup links to it and its Techniques-list / Solve Path rows get their ? (`TechniqueLearnButton` in App.tsx, which shows only when `tutorialTargetFor` returns a target). To teach a different position, change the board string and the digit/cell there; if a finder's wording or behaviour changes, a lesson that no longer matches is skipped with a console warning rather than breaking the page.
- **Adding a setting**: put its default in `DEFAULT_SETTINGS` (`src/settingsDefaults.ts`), start its `useState` from `initialSettings` (the saved value, else the default), add it to the `currentSettings` snapshot and its deps (saving + analytics; a non-boolean also needs a check in `persistedState.ts`'s `readSetting`), reset it in `resetSettingsToDefaults()` (Settings → "Reset to defaults"), add its control to the right toolbar menu (Generate Puzzle, Dragon Configuration, or Settings), and add an item to that menu's tab in `HELP_TABS` in `src/helpContent.ts` (the `?` help modal, one tab per menu; plain data the user edits by hand, with `settingKey` pulling the live default).

Before changing anything Dragon-related (finder rules, Dynamic/Rule 3, AIC limits, move log, replay UI, auto-solve, generator), read `DRAGON_COLOURING_HANDOFF.md` at the repo root. ## Conventions

- UI cell notation is 1-indexed `r3c4`; code is 0-indexed. Notation strings use words: `r3c4 is 5`, `r4c8, r6c8 => r4c7 is not 4`.
- Comments explain *why* (tradeoffs, past bugs) at length; match that in the finders.
