# Dragon Colouring handoff

Purpose: let a fresh session change how features treat Dragon Colouring (rules, Dynamic Dragon, UI replay, auto-solve, generator, solve path) without re-deriving the algorithm or silently changing its semantics.

**Provenance.** Reconstructed by reading the code on 2026-09-20; the session that produced this file did no Dragon debugging or experiments. Everything under "Confirmed" was checked against the source at that date. "Observed, not reproduced" = spotted by reading, never run. "Ideas" = unverified. The README claim that Dragon solves all Sudoku.Coach Hell / Beyond Hell puzzles is the author's, not re-verified. The Dragon files were heavily modified and uncommitted at the time (`SudokuDragonFinder.ts` +352/-108 vs HEAD; `SudokuHiddenPairFinder.ts` and `SudokuShortAicFinder.ts` untracked) - check `git status` before assuming HEAD matches.

There is no test suite. Verification is: `npm run build` (type-check), the in-app "generate Dragon / Dynamic Dragon puzzle" buttons, and importing Sudoku.Coach puzzles. `frontend/scratch-*.ts` are stale (only plain Dragon and an older technique subset, no runner) and cannot exercise Dynamic Dragon.

## Concepts (confirmed)

- **Medusa chain** = a connected component (>= 2 nodes) of the strong-link graph over (cell, digit) candidates, two edge kinds: *bilocal* (digit has exactly 2 places in a unit) and *bivalue* (cell has exactly 2 candidates). Each edge means "exactly one of the two is true", so the component is 2-coloured `blue`/`yellow`. Components with an odd cycle are silently dropped by `findChains`. Which of the two colours is `blue` is arbitrary (first node reached), so never attach meaning to "blue" beyond "side A".
- **Two sides.** Side A = blue, side B = yellow. Exactly one side is true. Each side has a *primary* colour (Medusa colour) and a *secondary/dragon* colour (`blue`/`darkBlue`, `yellow`/`orange`; UI labels light blue / dark blue / yellow / orange). `sideOf()` maps any of the four colours to a side.
  - Primary node: true **iff** its side is true.
  - Secondary node: true **if** its side is true (one-way; converse unproven).
- **Promotion** turns a secondary into a primary when it is proven equivalent to its side (below).
- **Dragon Colouring only applies to a *stuck* chain**: none of Medusa's own mass elimination / rules 3-5 fire for it. `extend` does not check this; callers do, and the identical 4-line predicate is **copy-pasted in four places** (`computeStuckDragonExtensions`, `computeStuckDynamicDragonExtensions`, generator `buildRobustCheckpoint`, generator `applyOneDragonRound`). Change all together.
- **Snapshot semantics.** `board`/`candidates` are never mutated during `extend`. Extension Rules 1-2 read the real candidates. The hidden-single check and Extension Rule 3 reason on a *cloned hypothetical board* (`buildHypotheticalBoard`): every node of the assumed side (primary and secondary) is placed as a given and `eliminatePeerCandidates` is applied. The strong-link graph is built once, lazily, from the **real** candidates (only used by medusa-growth), so links created by hypothetical eliminations are never used except inside the AIC search on the hypothetical board.

## `extend()` main loop (confirmed; order matters)

`extend(medusaChain, board, candidates, {dynamic, allowedRule3Techniques, aicLimitPerStep})` returns `{moves}` or `null`. Every iteration:

1. **Eliminations** (`findEliminationMoves`) over all current nodes, using *sides*, not exact colours. If anything is found, append it and **return** (chain grows only until the first elimination exists). Otherwise, if exactly one side covers every empty cell, append a `solution` move (`findColouringSolutionMove`) and return - with or without exhaustive (see below). If a mass elimination exists it is returned alone; otherwise all Rule 3 + Rule 4 + Rule 5 finds are appended (Rule 3s, then 4s, then 5s), one `DragonMove` per find.
2. **Promotion** (`findPromotionMove`), before any extension, then `continue`. A pair of nodes (a, b) promotes when they are on opposite sides, not both already primary, and either (i) same digit in the same unit or (ii) same cell. Reasoning: they cannot both be true, and exactly one side is true, so a<=>A and b<=>B. Each secondary in the pair becomes its side's primary (`buildPromotionMove` lists only the recoloured nodes). Terminates because each promotion strictly reduces the number of secondaries. Right after a promotion, `findMedusaGrowthMove` runs `growChainFromGraph` from each promoted node (now known-true, so its strong links are usable) and colours newly reachable candidates as primaries (`medusa-growth`). Promotion/growth don't take part in turn alternation.
3. **Extension**, for the side whose turn it is (`turnPrimary`, starts `blue`): Rule 1 -> Rule 2 -> hidden single -> (only if `dynamic`) Rule 3. If the turn-side has none, the same chain is tried for the other side. After any extension move `turnPrimary` flips to the opposite of the side that just extended. If neither side yields a move: **return `null`** (whole partial colouring discarded).

**Exhaustive mode** (`options.exhaustive`, UI "Exhaustive Dragon Colouring", App default ON; finder/generator default OFF, which is exactly the behaviour above). Only a *non-mass* elimination changes: it is recorded, applied to a private copy of the candidates (`workingCandidates`; the strong-link graph is reset), and the loop continues with `continuing = true`, where the per-iteration order becomes promotion -> eliminations -> extension (before the first elimination it stays elimination -> promotion -> extension, so the first elimination is identical to OFF). Every promotion/extension stays its own move. Ends when: a **mass elimination** is found (kept as the last move); `findColouringSolutionMove` finds that exactly one side's nodes (primary or dragon) cover every empty cell (terminal `kind:'solution'` move, relies on puzzle uniqueness, checked after mass elimination and skipped if both sides cover; not exhaustive-only, see the 2026-09-25 fix below); no dragon (secondary) node remains after promotions; or no extension exists. The last three cut the log back to `lastEliminationEnd` (the end of the last elimination group), so results never end on promotions/extensions that led nowhere. Whether `extend` returns `null` is decided by the first elimination (or solution) and is the same on/off, so the plain-vs-Dynamic classification (and the generator) call it with exhaustive OFF. The spec's "a colour completely eliminated -> stop at the previous elimination" is only reachable as a mass elimination in practice (Rules 3-5 never eliminate coloured nodes), and that step is kept, per the "stop at that elimination step" rule. Cost is roughly 2.5-4x per `extend` call in a quick measurement, and it runs live on every board change and in the solve-path search.

**Optimize Dragons** (`options.optimize`, UI "Optimize Dragons", default OFF; Find by elims always forces it ON). OFF runs the loop above untouched (`extend` branches to `extendOptimized` right after option parsing, so OFF is byte-for-byte the old path). ON splits the run into *phases* (seed or last applied exhaustive elimination -> next elimination/terminal). Per phase: (1) run the default alternating strategy as a baseline (`runBaseline`, same per-side memo); if it dead-ends, the phase dead-ends exactly as OFF, so ON never changes *whether* a chain resolves (the plain-vs-Dynamic split and the generator call `extend` without `optimize` and rely on this); (2) breadth-first search over **every** extension either side could take next (`allExtensions`: every Rule 1, Rule 2 and hidden-single hit, via the `extensionRule1Moves`/`extensionRule2Moves`/`extensionHiddenSingleMoves` collectors, whose `limit = 1` form is what the default loop's `find*Move` methods return - same scan order, so OFF is unchanged), strictly shallower than the baseline's extension count, states deduped by `colouringSignature` (candidate+colour set) before `settle`; the first state at the shallowest depth reaching an elimination (or `solution`) wins; (3) past `OPTIMIZE_MAX_SEARCH_STATES` (3000 colourings; 500 for exhaustive's later phases, whose baselines are usually far deeper than any search reaches) the baseline stands. Rule 3 (Dynamic) is only a per-side fallback when that side has no plain extension, first find only. A side's extensions are cached per phase keyed by that side's own colouring (`sideExtensionCache`), computed from its own nodes and filtered per state for candidates/cells the other side has coloured - identical moves, but a side that isn't changing isn't rescanned or re-simulated for every state of the other. `settle` reproduces the loop's between-extension order (promotions, eliminations, solution/no-secondary checks) exactly. **History:** the first version (2026-09-23) branched only on which *side* extends, each side taking its first hit - so when one side had no extensions at all the search was just the default path. User-reported case (Sudoku.Coach position, Medusa 9r6c4/9r8c5/9r9c1/6r8c2 blue vs 9r6c5/9r8c2 yellow): yellow never extends, light blue's fixed scan order took 22 extensions to a mass elimination, while 3r8c3 -> 4r8c8 -> 4r6c7 (a hidden single, lowest priority and invisible to Rule 1, which ignores dragon colours) gives a Rule 5 on 4r6c5 in 3; now found, by the panel and Find by elims. Checked with a scratch harness on 20 generated Dragon/Dynamic puzzles x dynamic/exhaustive: 0 resolve/null mismatches vs OFF, 0 cases with more first-phase extensions, 0 unsound eliminations vs the true solution; 83% of chains needed fewer first-phase extensions (898 saved, vs 118 with side-only branching); ~5-9x the OFF cost, max ~300 ms/chain. In dynamic mode the plain search's Rule 3 fallback is budgeted too (`OPTIMIZE_MAX_RULE3_FALLBACK_SIMULATIONS`, 60 fresh simulations, 15 in later phases); past it a colouring reuses a Rule 3 move inherited from its ancestors (`OptimizeState.rule3Known` - a move derived from some of a side's candidates stays valid when the side has more), which cut all-techniques+exhaustive from 11.2 s to 4.2 s on a 14-puzzle set with the same first-phase results.

**Optimize Dynamic Dragons** (`options.optimizeDynamic`, UI "Optimize Dynamic Dragons" in the Dynamic Dragon Colouring section, default OFF; App passes `optimize: optimize || optimizeDynamic` for Dynamic chains only, so it works without plain Optimize; Find by elims follows the setting rather than forcing it). Adds a second search per phase after the plain one, bounded to fewer extensions than the plain one found (so never worse than plain Optimize - running it *instead* was, because its wider branching hits the state budget sooner), in which every Rule 3 move is a branch, not only a fallback. `extensionRule3Moves(..., limit)`: `limit` 1 is `findExtensionRule3Move` exactly (verified: 0 mismatches vs a pre-refactor copy on every OFF option combination except the recolouring fix below); `Infinity` records each forced candidate and keeps simulating (the forced candidate left unplaced, skipped from then on). Budgets: `OPTIMIZE_MAX_RULE3_SIMULATIONS` (20 fresh every-move simulations, 2 in later phases) and `MAX_RULE3_ENUMERATION_AIC_SEARCHES` (4 AIC searches per every-move simulation - capping all steps instead cost as much quality with AICs off as on). Measured on 14 Dynamic-only positions (first-phase extensions, OFF / Optimize / +Dynamic): default techniques 234 / 144 / 47; all techniques incl. unlimited AICs 295 / 188 / 82; 0 resolve mismatches, 0 worse, 0 unsound; worst chain ~250 ms (default) / ~350 ms (all + exhaustive).

**Performance regression investigation (2026-09-23).** Reported: with Optimize Dynamic ON, all AICs and the AIC limit OFF, some puzzles froze the page on load and the solve path timed out. Reproduced with the app's own `buildSolvePath` (bundled for Node) only with **Exhaustive OFF**, where every Dragon is its own solve-path step: OFF solved in 41-49 steps (3.6-6.3 s), ON timed out after 12-21 steps - ~10x per step. Root cause, the same for all three puzzles: not the AIC finders (a few % of the time) but the Optimize search's volume - thousands of colourings per chain, each paying a full elimination check (37% of the time) and Rule 1/2/hidden-single rescans, plus hundreds of Rule 3 simulations of which ~45% re-ran finders on a grid already simulated (the default path, fallback and every-move simulations of one colouring step through identical grids). AIC limit OFF amplifies it (deeper default paths, more Rule 3 branches) but genuinely pays: under Optimize Dynamic it resolved 83 Dynamic chains vs 59 with the limit on, 23 of the first-stage moves using 2+ AICs. Fixes, all exact (0 mismatches in 8540 full `extend()` output comparisons against the pre-fix code, every option combination): `hasAnyElimination` pre-check, `seenByNodes` tables for Rule 1/2, allocation-free hidden-single scan, `memoFind` finder cache (above), numeric `colouringSignature`. Results: `extend()` 3.2x faster across all settings (153 s -> 48 s); solve path, Exhaustive ON, 2-3.3x faster with identical steps; Exhaustive OFF + AIC limit OFF, case 1 now completes (11 s, 46 steps), cases 2/3 still reach the 12 s budget but ~1.5-2x further in. Remaining bottleneck: the number of fresh every-move Rule 3 simulations (~1700 per 41-step path, ~4 ms each, 85% of that inside the finders - short AIC search, subsets, UR); reducing it means changing which states the search expands or its budgets, i.e. results. Passed through `computeStuckDragonExtensions`/`computeStuckDynamicDragonExtensions` (panel, auto-solve, solve path); not used by the generator or the tutorial. Find by elims (`SudokuDragonTargetFinder`) always passes `optimize: true` regardless of the setting - shortest logs to cut, and no chain gained or lost since Optimize never changes which chains resolve.

Consequences: a returned result always ends with elimination move(s) (or a `solution` move); dynamic Rule 3 for side X runs *before* plain rules for side Y (order is per side, not "all plain first"); the caller is what guarantees plain-before-dynamic (see below).

Each extension move colours exactly one new candidate with the side's secondary colour; an already-coloured candidate (any colour) is never re-coloured except by promotion, which guarantees termination.

### Extension rules, exact conditions

- **Rule 1** (`findExtensionRule1Move`): for a unit and digit with >= 2 unsolved candidate cells, count the cells that do **not** see a *primary*-coloured node of that side with the same digit (`seesColor`, own cell excluded). If exactly one such cell and its candidate isn't coloured -> colour it secondary. Note it looks at the primary colour only, unlike Rule 2. (Observed: this is likely subsumed by the hidden-single check, which uses the fuller hypothetical board; not tested. Rule 1 still wins the race and so sets the reported `kind`.)
- **Rule 2** (`findExtensionRule2Move`): unsolved cell with no already-coloured candidate; among its candidates, those not seeing a same-side node (**primary or secondary**, `seesSide`) of the same digit; exactly one survivor -> colour it secondary.
- **Hidden single** (`findExtensionHiddenSingleMove`, always on, *not* a "dynamic" technique): on the hypothetical board, first unit (rows, then columns, then boxes; digits 1-9) where a digit has exactly one candidate cell and that candidate isn't coloured -> secondary. Design decision (commit `656a576` "removed hidden singles from dynamic dragons"): it is plain-Dragon logic, so `'hidden single'` never appears in a move's `dynamicTechniques` or in the "Dynamic Dragon Colouring (...)" label.
- **Rule 3, Dynamic only** (`findExtensionRule3Move`, next section).

### Elimination rules (side-generalised Medusa, `findMassElimination`/`findRule3/4/5`) - confirmed and reasoned sound

Mass elimination (checked in this order): (1) two nodes in one cell on the same side; (2) same digit, same unit, same side; (3) an uncoloured unsolved cell where every candidate sees a node of one side. Any of these proves that side false. `buildMassMove` then: **eliminates only the false side's *primary* nodes** and **solves every node (primary and secondary) of the true side**. A false side says nothing about its secondaries (denying the antecedent), so they are not eliminated. `provenTrueColor` records the conclusion; the UI summary says "X is true".
Rule 3: uncoloured candidate seeing the same digit on both sides. Rule 4: cell with a node of each side -> every uncoloured candidate in it. Rule 5: cell with exactly one coloured node; another candidate there sees the same digit on the opposite side.

## Dynamic Dragon = Extension Rule 3 (confirmed)

Dynamic mode differs from plain **only** by allowing Extension Rule 3 as an extra last-resort extension. `findExtensionRule3Move` simulates on the hypothetical board for up to `MAX_RULE3_SIMULATION_STEPS` (200) iterations. Each iteration tries, in this fixed simplest-first order, and applies **only the first instance that has eliminations** (mutating `hypCandidates` only), then restarts from the top:

hidden single -> locked candidate -> naked pair -> naked triple -> naked quad -> hidden pair -> Unique Rectangle (any of Types 1/2/3/4/5/7a/7b/7c/7d, simplest-type-first via `TYPE_PRIORITY`) -> BUG+1 -> Bivalue Oddagon -> AIC (single-digit or general).

After each application it checks `findNewlySingleCandidateCell` (an uncoloured cell reduced to exactly one candidate). If found, that cell/digit is coloured secondary and the move is finished (`buildRule3CombinedMove`). A hidden single found in the simulation, a UR instance with a `solvedCandidates` entry (only Type 1 ever produces one), or a BUG+1 find (always a full direct solve, so its block returns immediately rather than ever being kept as a chain antecedent) is itself the conclusion. If the loop runs dry or hits the cap -> `null` (steps discarded). Applications that didn't force anything are kept as chain steps.

- `allowedRule3Techniques`: `naked pair` is always re-added by `extend`. In the UI the `hidden single`, `locked candidate` and `naked pair` checkboxes are disabled (always on). `DEFAULT_RULE3_TECHNIQUES` = everything except the three AIC kinds, so AICs are opt-in; `bivalue oddagon` and `BUG+1` are both on by default alongside everything else.
- **Dependency pruning** (`selectRelevantChainSteps`): walks the recorded steps backwards keeping only those whose `affectedCells` intersect the dependency set (final basis cells, growing with kept steps' basis cells). Result: `dynamicTechniques` lists kept antecedents + the final technique (minus `'hidden single'`), `dynamicTechniqueCells` lists their basis cells. Hidden single passes its whole unit as the dependency set (`dependencyCells`, `buildRule3CombinedMove`'s last param).
- **One `Rule3ChainStep` shape for antecedent and final.** Each technique block in `findExtensionRule3Move` builds one `Rule3ChainStep` (`clause` = detailed "a naked pair of {1,8} in {...}, which eliminates ..." from the `*Clause` builders; `summaryName` = just "a naked pair" / "a short single-digit AIC (Type 1)"), then either passes it to `buildRule3CombinedMove(primary, steps, final, colored, conclusion)` if a cell got forced, or pushes it onto `steps`. `Rule3Conclusion` (`single candidate` / `hidden single` / `direct`) only chooses the wording of the closing colouring clause (`rule3ExtensionClause`).
- **Description vs substeps.** `description` only names the techniques: "Assuming light blue is true, then we have a naked pair, which reveals a short single-digit AIC (Type 1). As a result, r2c8 will only have 1 option (6), so colour 6r2c8 dark blue." The detail lives in **`DragonMove.substeps`** (`DragonRule3Substep[]`): one entry per kept technique (antecedents + final, `'hidden single'` excluded like `dynamicTechniques`) - `{ technique, clause, basisCells, eliminatedCandidates, aic? }` - then always a closing `'dragon colour extension'` entry (the "As a result, ..." clause, basis cell = the coloured cell, no eliminations). So every extension-rule3 move has >= 2 substeps and always shows the substep player. Lets the UI (App.tsx's `DragonStepper`) reveal the chain one substep at a time via a second, separate forward/rewind control, with the new colour only appearing at the last one, instead of always showing the whole chain's basis cells/eliminations at once (which remains the default, unnavigated view - see below).
- **Emptied cell.** A mass elimination proven by an uncoloured cell whose every candidate sees one side carries `DragonMove.emptiedCell`; the grid gives it the same yellow border (`medusa-highlight-cell`) 3D Medusa gives its own emptied cell, while that move is on screen.
- **Plain vs dynamic classification lives in the callers.** `computeStuckDynamicDragonExtensions` skips a chain if plain `extend` already succeeds on it, so a chain never appears as both. The panel name is `Dynamic Dragon Colouring (<techniques used, fixed order>)`.
- UR Type 1 in the simulation implicitly relies on the puzzle having a unique solution (as do all the other UR sub-types, and BUG+1 and Bivalue Oddagon - every uniqueness-based technique shares this assumption).
- UR's block branches on which of `UniqueRectangleInstance.solvedCandidates`/`eliminatedCandidates` is non-empty (`ur.solvedCandidates.length > 0` for a direct solve, otherwise eliminate-and-check-for-a-newly-forced-cell) rather than switching on `ur.type`, so a future UR sub-type that can solve needs no new code here - it only needs to populate `solvedCandidates` correctly.

### AIC handling (confirmed)

- Run on the *hypothetical* candidates via `findShortAics` (length 3 or 5, strong-weak-strong[-weak-strong], one chain kept per elimination set). `classifyShortAic`: `single-digit` = length 3 and one digit; everything else `general`. Gated by the technique being in `allowedTechniques`.
- Limit: `aicLimitPerStep` (UI "Limit to 1 AIC per step", default on) means at most **one AIC application per `findExtensionRule3Move` call**, counting every AIC *tried* (`aicStepsUsed`), not only the ones that end up relevant. Off = unlimited within the call's 200-step cap.
- Every chained technique's eliminations only mutate the *hypothetical* candidates, never the real board - the move's own `eliminated` is always `[]` for extension-rule3. Drawn as a hollow circle + faint cross (`technique-hypothetical-elimination` in App.css), not the solid red `technique-eliminated` pip. This used to be AIC-only (`aicChains[].hypotheticalEliminations`, kept for backward compat - the tutorial still reads it directly); it's now generalized to every technique via `DragonMove.substeps[].eliminatedCandidates` (a Locked Candidate's, a naked pair's, ... not just an AIC's), which is what the live grid (App.tsx's `dragonAssumedEliminations` memo) actually reads today. `aicChains` still gets the AIC purple-chain node/link drawing either way.
- Master switches: `shortAicEnabled` (default **off**) and `shortSingleDigitAicEnabled` (default **on**) strip the matching kinds via `effectiveAllowedRule3Techniques`; but since the checkbox set defaults to no AIC kinds, Dynamic Dragon uses no AIC until the user ticks one.
- **Generic AIC** (`'generic aic'`, `SudokuGenericAicFinder`, chains of 7 up to `GENERIC_AIC_MAX_LENGTH` links) is a third AIC kind with the same master-switch/limit behaviour: `genericAicEnabled` (needs Short AIC on), stripped by `effectiveAllowedRule3Techniques`, counted by `aicLimitPerStep`, and tried *last* in Extension Rule 3 (the generator function only starts the generic search once no shorter AIC applied, and not at all once the limit is used). The generator has a third flag `disregardGenericAic` (only settable OFF when `disregardAic` is OFF); with it OFF, almost every Dragon checkpoint is rejected (6/6 default-generated states contained a generic chain), so generation is far slower.
- Auto-solve: the "Dynamic Dragon Colouring" button drops whole chains whose moves list any AIC technique unless `dynamicDragonAutoSolveIncludesAics`.
- The standalone panel entries for AIC suppress eliminations already covered by easier techniques; the Dragon simulation does **not** apply that suppression.

## `DragonMove` semantics (confirmed)

Fields: `id`, `kind`, `description` (display text only; nothing parses it), `colored: DragonNode[]`, `eliminated`, `solved`, plus `provenTrueColor` (mass-elimination), `dynamicTechniques` / `dynamicTechniqueCells` / `aicChains` / `substeps` (extension-rule3 - see the AIC handling and Dynamic Dragon sections above for `substeps`).
Sequence: `moves[0]` is always `kind:'medusa'` with the whole seed chain coloured. Then any interleaving of `promotion`, `medusa-growth`, `extension-rule1|rule2|hidden-single|rule3`. Then the terminal group of `mass-elimination` **or** `rule3`/`rule4`/`rule5` moves (with exhaustive ON, several such rule3/4/5 groups can be interleaved with promotions/extensions, ending in a final group, a `mass-elimination`, or a `solution`). Only elimination/solution moves carry `eliminated`/`solved`. Ids: shared counter `${kind}-${n}` for extension/promotion/growth; terminal moves keep `id: ''` (nothing in the UI keys on it). State at step *k* = fold of moves 0..k.

## UI replay (confirmed)

- `TechniqueInstance` for Dragon has `moves`, empty `usedCells`/`usedCandidates`; `eliminatedCandidates`/`solvedCandidates` are the flattened moves' (used by solve path and summary). Instance id = `dragon-` or `dynamic-dragon-` + sorted chain-candidate keys (with colour initial), so selection is lost if the chain composition changes. Panel order: everything else first, then Dragon, then Dynamic, each sorted by `moves.length` ascending.
- `foldDragonMoves(moves, k)`: colour per candidate = *latest* colour among moves 0..k (promotion overwrites secondary with primary); eliminated/solved accumulate. Grid pips prefer `dragonHighlight.*` over the instance's static fields. `darkBlue`/`orange` exist only via the fold.
- `dynamicTechniqueCells` and `aicChains` are taken from the **current step's move only**, not folded.
- **Substep player** (`DragonStepper` in App.tsx, second/nested forward-rewind row, only rendered when `move.substeps.length > 1`): a *separate* piece of state from the main `dragonStepIndex` - `dragonSubstepIndex: number | null`, `null` meaning "not navigating, show every substep revealed" (the default, and the only state any move without >1 substeps ever has). `DragonStepper` resolves `null` against the move on screen's own `substeps.length` itself, so switching main step via `onDragonStep` needs no substep-specific bookkeeping beyond resetting `dragonSubstepIndex` back to `null` (a different move has its own, unrelated substeps). The grid's `dragonTechniqueCellKeys`/`dragonAicChains`/`dragonAssumedEliminations` memos all derive from `visibleSubsteps` = `substeps.slice(0, visibleSubstepIndex + 1)` - cumulative, so rewinding the substep player only ever *removes* basis cells/hypothetical eliminations from the grid, never partially. The move's own conclusion (the `colored` cell) is likewise withheld from `dragonHighlight`'s fold until the last substep is reached (`foldDragonMoves`'s `includeCurrentMove` param, `dragonReplay.ts` - every other caller keeps the default `true`, unaffected).
- The stepper is a walkthrough only: **Apply always commits the whole chain** (`fullTechniqueEffect` folds to the last move), a Dragon chain counts as **one** step in Solve Path, and `dragonStepIndex` resets to 0 on selecting another row.
- Auto-solve (`runDragonColouring`): unions every chain's solved/eliminated (deduped) computed against the same pre-apply snapshot and applies at once via `commitAutoSolve` (clears the cached solve path). Buttons: bivalue-seeded (`hasBivalueCellLink`), any Medusa, Dynamic. The panel's `minBaseMedusaFilter` (>= 3 base candidates) applies to the panel only; the auto-solve buttons pass 0.

## Puzzle generator coupling (confirmed)

`SudokuDragonPuzzleGenerator` removes clues one at a time (uniqueness via `SudokuSolver`) until a **freshly autofilled**, singles-only-solved checkpoint has: no locked candidates / pairs / triples / quads / hidden pairs / UR (any type) / BUG+1 / Bivalue Oddagon / Simple Colouring, every Medusa chain stuck, and Dragon (or, with `requireDynamic`, Dynamic-but-not-plain on at least one chain; with `requireDynamic` + `forbidPlainDragon`, plain Dragon fails on *every* stuck chain and Dynamic succeeds on at least one, so Dynamic Dragon is the only way forward) can progress. `forbidPlainDragon` positions are rare enough (~3.3 min of 14-worker search each on an 8-core Ryzen 7700X with all AIC kinds not disregarded: 31 in ~92 min across two runs) that the app never generates them live: the "Dynamic Dragon puzzles must not allow plain Dragon" setting (`dynamicDragonPuzzleForbidsPlainDragon`, default OFF) serves one from `dynamicDragonPuzzleStockData.ts` via `pickStockDynamicDragonPuzzle` (`dynamicDragonPuzzleStock.ts`), which applies a random Sudoku symmetry and re-verifies it with `checkPuzzleState` under the current settings, falling back to the untransformed original. It then confirms full solvability by alternating an easy-technique grind with one `applyOneDragonRound`. Short AIC is checked per kind (`classifyShortAic`) and only when that kind is *not* disregarded: `generate({disregardSingleDigitAic, disregardAic})`, both default **true**, so by default a checkpoint may still have an AIC available next to the Dragon technique. The grind (`applyShortAic`) still uses every AIC regardless. The Settings "Puzzle generation" toggles feed these; `App.tsx` handlers keep the invariants (Short AIC enabled => Single-Digit AIC enabled; a disregard flag is only false while its technique is enabled; disregard-AIC only false while disregard-single-digit is false). Turning Short AIC ON asks for `window.confirm` because non-disregarded AIC makes generation slower. The generator hardcodes its own finder lists (adding a technique means touching both the "nothing easier" check and the grind) and **never receives the UI's Rule 3 technique set or AIC limit**: `generate({requireDynamic})` uses `extend`'s defaults (no AICs). The Settings hint claims the technique set applies "for both puzzle generation and solving"; the code does not do this for generation.

**Performance (`reduceUntilDragonNeeded`/`buildRobustCheckpoint`/`solveWithSinglesOnly`).** Profiling the worst realistic case (`requireDynamic: true` with every AIC kind's disregard OFF - the rarest target, since it demands zero AIC anywhere on the board *and* that Dynamic Dragon specifically, not plain, be what's needed) found `buildRobustCheckpoint` was called on essentially every single clue removal across the whole reduction, but ~95% of those calls rejected on their very *first* check (`isFullySolved` - naked/hidden singles alone still solve the board), and `solveWithSinglesOnly` (which every call starts with) was by far the single largest cost in the entire generator.
- `solveWithSinglesOnly` used to fully re-autofill the whole board's candidates from scratch (`createEmptyCandidates` + a fresh `SudokuRules.isSafe` sweep of every empty cell) at the top of *every* round of its singles loop, even though only the handful of cells a round just solved actually changed. It now autofills once and maintains candidates incrementally via `SudokuRules.eliminatePeerCandidates` after each placement instead - provably identical results (autofilling is a pure function of board legality; placing a digit only ever changes its own peers' legality for that one digit), verified against the old version across ~900k comparisons with 0 mismatches before switching.
- `PHASE1_CLUE_THRESHOLD` (in `SudokuDragonPuzzleGenerator.ts`) skips calling `buildRobustCheckpoint` at all above 55 remaining clues, rather than calling it and paying for `solveWithSinglesOnly` only to have `isFullySolved` reject it anyway - not a probabilistic shortcut: once a board is fully solved by singles alone, it has no empty cells left, so *every* other check `buildRobustCheckpoint` would run after `isFullySolved` (locked candidates, pairs, subsets, hidden pairs, UR, BUG+1, Bivalue Oddagon, Simple Colouring, AIC, Medusa/Dragon) is necessarily a no-op against it too - the skip and the full call always agree. Calibrated with a dedicated ~900k-trial sweep (see the constant's own comment) that found singles alone were *always* still sufficient above 51 remaining clues; 55 keeps a safety margin above that observed ceiling. Together these roughly doubled the worst-case success probability within a 30s budget in benchmarking (~25% -> ~35-40%, 8-trial samples) via a ~1.5x per-call speedup plus skipping the ~83% of calls that were happening above clue count 45 - but the underlying target (a checkpoint with *zero* AIC anywhere on the board *and* specifically requiring Dynamic Dragon) is rare enough on its own that a reliable sub-30s guarantee wasn't reached; see "Parallel generation" below for what closed that gap (Web Worker parallelism plus a bitmask `solveWithSinglesOnly`); a dependency-tracked incremental clue-removal that avoids recomputing `solveWithSinglesOnly` from scratch on every removal is still an untaken option. Re-run the calibration sweep before changing `PHASE1_CLUE_THRESHOLD`, and re-verify equivalence before changing how `solveWithSinglesOnly` maintains candidates.

**Simple Colouring / 3D Medusa targets.** `generate({target})` also builds "Simple Colouring practice" and "3D Medusa practice" puzzles through the same checkpoint pipeline: `buildRobustCheckpoint` runs the usual easier-technique checks, then for `'simple-colouring'` accepts as soon as Simple Colouring rule 1/2 applies, and for `'medusa'` requires Simple Colouring to fail and some Medusa chain to be non-stuck (mass elimination or rule 3/4/5). Both skip every AIC check (Simple Colouring and Medusa eliminations are always also AICs) and ignore `requireDynamic`/`forbidPlainDragon`/`disregard*`; the rest-of-puzzle solvability check may use Dynamic Dragon rounds (`solveWithDynamic`). Single-thread, 40 runs each: Simple Colouring 0.3 s median / 1.3 s max, Medusa 0.6 s / 2.8 s, all independently verified.

**Parallel generation (`ParallelDragonPuzzleGenerator.ts`, `dragonPuzzleGenerator.worker.ts`).** Both "generate Dragon / Dynamic Dragon puzzle" buttons call `generateDragonPuzzleInParallel`, which starts `hardwareConcurrency - 1` module Web Workers (capped at `MAX_WORKERS`), each running `generateBlocking` (the non-yielding twin of `generate`) with identical options over its own random solved grids; the first non-null result wins and every worker is terminated (termination is the only cancellation - `generateBlocking` never yields). A main-thread timer at budget + `DEADLINE_GRACE_MS` backstops workers that overrun their own between-attempt deadline check. No Worker support, or every worker failing to start/crashing, falls back to the main-thread `generate` with the remaining budget. Qualification is unchanged: every worker runs the same checks, so this only changes how many random grids get tried per second.

Profiling one worker in the worst case (`requireDynamic`, all three disregard flags OFF) showed the Dragon/AIC/technique checks are ~2% of the time: the cost is `solveWithSinglesOnly` (~57%, mostly `SudokuSingleFinder.findHiddenSingles`' per-unit array allocations) and the per-removal uniqueness check (`SudokuSolver.countSolutions`, ~37%). `solveWithSinglesOnly` is now a row/column/box bitmask fixed-point search (order-independent because the clue set is always uniquely solvable when it's called - see its comment), verified identical (board + candidates) to the `SudokuSingleFinder` version on 250,039 reduction states from 4,416 grids, 0 mismatches, 4.4x faster. The uniqueness solver is the next hot spot and is untouched (shared with validation/`SudokuGenerator`).

Benchmark (Node `worker_threads` running the same code, Ryzen 7 7700X 8C/16T, worst case above; "attempts" = random solved grids fully reduced):

| Setup | Attempts/s | Time to puzzle (mean / median / max) |
|---|---|---|
| Before: 1 thread | 184 | 60.6 s / 61.0 s / 122 s (12 runs; an earlier 9-run sample averaged 26.7 s - the distribution is very wide) |
| Workers only: 8 | 897 | 11.3 s / 7.7 s / 58.9 s (25 runs) |
| Workers only: 15 | 917 | 11.6 s / 6.9 s / 34.1 s (25 runs) |
| Bitmask singles, 1 thread | 325 | - |

Throughput scales ~linearly to the 8 physical cores and then flattens (12 workers: 970/s, 15: 917/s with the old singles), so SMT siblings add little; a machine with fewer cores gets proportionally less. Time to puzzle is roughly exponential (each grid is an independent lottery ticket), so the mean tracks 1/throughput and the tail stays long.

## Invariants to preserve

1. Exactly one of side A / B is true; every deduction must be valid under both cases. Don't relax mass-elimination's "primary-only eliminated, all true-side solved" asymmetry.
2. A candidate has at most one colour in `nodeMap`; only promotion recolours.
3. Candidate marks must be accurate: strong links and every hypothetical technique trust them (the app separately flags inaccurate candidates).
4. Plain vs Dynamic must stay disjoint per chain, and hidden single stays outside `dynamicTechniques`.
5. `extend` must stay side-effect free on `board`/`candidates` and cheap: it runs live on every board/candidate change (`useMemo` in `App`), from the solve-path search, and hundreds of times per generated puzzle. Rule 3 clones the board and reruns whole-board finders (incl. the AIC search) up to 200 iterations per call, per side, per extension move; the solve path's 12 s budget is only checked *between* steps (and running out of it must never be read as "stuck" - see `solvable-unknown` in App.tsx). `extend`'s loop alternates turns between the two sides, and each side's own Rule 3 simulation only ever depends on that side's own coloured cells - so once a side's turn comes up empty, it stays empty until that side gains a cell or (exhaustive only) the working candidates change; this is memoized (`rule3Nothing`/`candidatesVersion` locals in `extend`) rather than re-simulated every alternating turn. Any change to what a side's hypothetical board is built from (`buildHypotheticalBoard`) must keep that memo's invalidation in sync.
6. New/changed techniques usable inside Rule 3 need: `Rule3Technique`, `ALL_RULE3_TECHNIQUES` (single source of truth, also drives the settings checkboxes), a branch in `findExtensionRule3Move`, antecedent + final clause builders, and `RULE3_TECHNIQUE_LABELS` in `App.tsx`; plus the generator lists above.

## Known issues / edge cases

Fixed (2026-09-25): **Exhaustive ON solved puzzles OFF called brute force.** The `solution` check used to run only while `continuing` (after an exhaustive-mode elimination). A fresh chain whose side filled the whole grid before any elimination then dead-ended (the other side had nothing left to extend) and returned `null`, on or off - so the only way to reach that solution was an exhaustive continuation that happened to start before it. User case (Sudoku.Coach position `800000500004050001060000030080005020100400900009706000000090004900003080050600300`, every Dynamic technique, AIC limit off): ON solved in 3 steps (one Dynamic Dragon whose yellow side fills the grid after two Rule 5s); OFF took a Locked Candidate at step 3 instead (greedy), then two Dynamic Dragons, then no chain resolved from scratch, even with Exhaustive ON. Now both loops (`extend`, `extendOptimized`'s `settle`) check it whenever no elimination is pending; OFF solves it in 6. Sweep over the Dynamic stock under 6 option combinations: 0 unsound eliminations/solves. 4 of the 31 stock positions became plain-Dragon-solvable this way and were dropped (27 left).

Fixed (2026-09-23): Extension Rule 3's direct-solve branches (UR Type 1, BUG+1, Oddagon Type 1) returned their forced candidate without checking it was uncoloured, unlike every other extension path - so one could recolour the other side's dragon node (seen: UR Type 1 turning an orange 2r8c2 dark blue), breaking invariant 2 and the per-side memo's "nodes only grow" assumption. Found by the equivalence sweep for the `extensionRule3Moves` refactor (4 of ~2000 exhaustive Dynamic logs changed, all this). They now skip it and the simulation carries on. Note the skipped case is itself a deduction left unused: both sides forcing the same candidate proves it true (see Ideas).

Observed, not reproduced:
- **Dependency gap in explanations.** `buildRule3CombinedMove` tracks dependencies from the final technique's *basis* cells only (hidden single is the exception). A kept-worthy earlier step that only trimmed the *forced* cell (not the basis cells) is dropped, so the description / `dynamicTechniques` label can omit a technique the conclusion depended on. The colouring itself remains sound.
- Rule 1 counts only primary visibility (see above).
- `growChainFromGraph` doc says traversal "stops at an already-known node"; the code keeps traversing through known nodes (only *reporting* is filtered). This is sound, since strong links are exact-one-of relations, but the comment is wrong.
- Terminal rule 3/4/5 moves can eliminate the same candidate twice, so the summary "eliminates N candidates" can over-count (applying is idempotent).
- Contradictions in the hypothetical are ignored: `findNewlySingleCandidateCell` / `findNewlyHiddenSingleCell` skip candidates already coloured (by any colour), so "assumption A forces a candidate that B has coloured" is not used as a proof.

Unresolved from earlier work (prior conversation, from memory notes dated 2026-09-18, not re-checked): the user's worked examples for 3D Medusa rules 3-5 didn't match their claimed results (rules 1-2 did). Dragon's rules 3-5 are generalisations of those, so a fix there may need to be mirrored.

## Ideas (unverified; each changes intended semantics, so ask the user first)

- Treat an empty hypothetical cell / digit with no place in a unit as "assumed side is false" (a contradiction rule; new mass-elimination reason).
